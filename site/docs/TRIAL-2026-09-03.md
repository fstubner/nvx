# Trial instantiations, 2026-09-03

Two runs, hours apart. The first found what the template still hard-coded;
the second, after those fixes and after the sample content replaced
netscli's, checked whether a site can be built from this repo by following
`AGENTS.md` alone.

---

## Second run: Sieve, a log filter

The question: can an agent take this repo and produce a working site for a
product it has been told about, without touching the shell?

Done from `git archive` of the tree at the time, following `AGENTS.md` in
its stated order. The product: a command-line log filter, three platforms,
**no desktop build**, docs on with three pages, the `split` layout, its own
accent. Chosen to exercise the paths netscli itself does not use.

### What happened

Every step worked as written. `check:content` went from 13 findings to 0.
`npm run theme -- --accent "#0ea5e9" --verify` re-branded twenty tokens and
passed the contrast sweep on its first attempt. The build produced six
routes; typecheck, the four static guards, the changelog check, the contrast
sweep and axe all passed. With `heroDownloads` empty the desktop button and
its menu did not render and the install command took the whole row, which is
what the empty list is for.

Total: about an hour, nearly all of it writing copy and docs pages.

### Three defects it found, all now fixed

1. **`AGENTS.md` and `modules.ts` both said turning docs off also needs the
   Starlight integration removed from `astro.config.mjs` by hand.** The
   config has read `modules.ts` since the generalisation sync. Building with
   `docs: false` gives three routes, no `/docs/` link anywhere, contrast and
   axe clean, and the config untouched.
2. **`check:content` identified the placeholder images by byte length**, and
   a replacement wordmark drawn to the same geometry in a different colour
   compressed to exactly the same 914 bytes -- so the check called a replaced
   asset untouched. It hashes the file now.
3. **The browser sweeps failed with a misleading timeout.** A hand-started
   `astro preview` binds `localhost`, which resolves to ::1 first on Windows,
   while the checks wait on 127.0.0.1: the reuse guard saw a free port, the
   spawn could not bind, and the run died 30 seconds later with a message
   that looked like a broken build. Fixed upstream in netscli, so netscli
   gets it too; the guard now names the process holding the port.

### What it did not cover

The `centered` layout (netscli's, and the one the screenshot baseline
covers), a product with `changelog: false`, and replacing the docs with a
larger set than three pages.

## First run: what the template still hard-coded

The question: can a new product start from this template by editing only
what the README says to edit? Done once, from the tree at the sync commit,
for a fictional product ("Ledgerly", a plain-text accounting CLI), in a
scratch directory. This is what happened.

## What was done

1. `git archive` of the template into an empty directory, `npm ci`.
2. Replaced `src/data/site-content/`: `meta.ts`, `hero.ts`, `footer.ts`,
   `surfaces.ts` (two cards), `install.ts` (three platforms, no desktop
   app), `faq.ts` (two items), the GitHub link in `nav.ts`, the version.
   Images left as netscli's placeholders. 856 lines of netscli content
   became about 130.
3. Built with `modules.docs = false`, then with `modules.docs = true` and
   the docs trimmed to two pages plus a two-entry sidebar.

## What worked

- Both variants build. Docs off: 3 routes (index, 404, changelog). Docs
  on: 5. `astro check` clean both times; every guard, the contrast sweep
  and the a11y sweep pass.
- No netscli text reaches the landing page. Measured on the built
  `index.html`: 0 visible mentions.
- `modules.docs = false` does what the README says: the Starlight
  integration is gone from the build, and the nav, footer, 404 page and
  surfaces copy stop linking to `/docs/`.
- The changelog check passes on a repo with no tags, because the stub
  `CHANGELOG.md` dates nothing.

## What did not

1. **The hero's "Desktop app" download menu is netscli's.** The five
   installer links and the per-OS swap are hard-coded in
   `src/components/Hero.astro` (lines 42 to 100) and
   `src/scripts/landing/os-tabs.ts` (line 161 on), not in `site-content/`.
   A product without a desktop app still shows netscli's `.msi`, `.dmg`
   and `.AppImage`. The July generalisation had a `hero.downloads` field
   for exactly this; netscli's code never adopted it, so the field was
   dropped in the sync. The fix belongs in netscli first (one source: the
   `desktop` entries `install.ts` already has), then here.
2. **The docs sidebar lives in `astro.config.mjs`.** A product's docs
   structure is content, and the trial had to edit the config to remove
   nine entries whose pages it had deleted. Starlight did not fail the
   build on the stale entries; it built links to nothing.
3. **The docs' own cross-links are content, and netscli's docs link to
   each other.** With two pages kept, `dist/docs/index.html` linked to six
   that do not exist. Expected for a reference example, but the build says
   nothing, and nothing else checks internal links.
4. **Everything is still called netscli.** 410 `--netscli-*` token uses and
   26 `netscli-` class or attribute names in the built landing page. None
   visible, all generic, and every one a grep hit that means nothing.
5. **The reference images stay netscli's** until replaced; the README says
   so, and the trial did not replace them.

## What this means for the README's contract

"Edit `site-content/*.ts`, the docs, the assets and the changelog; nothing
else" held for copy, links and toggles, and not for the hero downloads or
the docs sidebar.

All five were fixed the same day, which is what the second run above then
tested: the hero's installer list and the docs sidebar, title, description
and logo became content; the `netscli-` prefix became `ui-`; and the
reference content became a fictional product's rather than netscli's, so
what a fork deletes is obvious. `npm run check:content` now reports what is
still the sample, including a sidebar entry whose page does not exist --
the one thing on this list nothing else could see.
